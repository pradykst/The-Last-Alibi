# Verified 0G suspect testimony

## Why 0G is load-bearing

The Last Alibi uses 0G Direct Compute for live suspect dialogue. A live utterance is not accepted merely because a provider returned HTTP 200 or valid JSON: the server requires the official SDK's per-response verification to return the boolean value `true` before it parses or returns any model-controlled content.

This creates two deliberately separate facts:

- **Inference provenance:** the response passed 0G's supported response-verification path.
- **Evidentiary authority:** the response remains `unverified-testimony` with no canonical effect and no candidate-mask effect.

TEE-backed response verification is not a zero-knowledge proof that a suspect's statement is true. It protects the inference path; it does not reveal or decide the hidden case.

## Selected interface

Alibi uses Direct 0G Compute through `@0gfoundation/0g-compute-ts-sdk` version `0.8.4`. The package requires the repository's Node.js 22 server runtime and is exposed only through `@alibi/zero-g/server`.

Direct Compute was selected because the official flow exposes an explicitly configured provider, provider service metadata, SDK-generated authenticated request headers, a real response identifier, and `broker.inference.processResponse(providerAddress, responseId)`.

The Router offers convenient routing and failover, but the current official comparison does not document an equivalent per-response verification artifact. Opaque provider failover would also weaken testimony provenance. Alibi therefore performs no provider failover and has no OpenAI, Anthropic, Gemini, or other conventional-provider fallback.

## Provider and service policy

The network, HTTPS RPC URL, provider address, expected model, and verification mode are deployment configuration. There is no built-in network, provider, model, wallet, or credential. On first use the adapter reads the live service catalog and requires the configured provider to:

- exist in the catalog;
- expose the configured model;
- be a `chatbot` service;
- report the configured verification mode (`TeeML` or `TeeTLS`); and
- expose an HTTPS endpoint.

Provider preflight and response verification are recorded separately. When `ZERO_G_REQUIRE_PROVIDER_VERIFICATION=true`, the adapter calls the SDK's `verifyService` support and requires a successful result before inference. Official 0G documentation warns that the automated signer/compose checks are not necessarily full attestation verification, so Alibi does not describe this status as full remote attestation.

## Per-response verification

Each non-streaming request follows this sequence:

1. Discover and validate the configured provider's live catalog entry.
2. Optionally run provider preflight.
3. Ask the SDK for authenticated request headers.
4. Send one bounded chatbot request to the validated HTTPS endpoint.
5. Enforce the configured timeout and maximum response size.
6. Reject non-success HTTP status or a malformed provider envelope.
7. Prefer the case-insensitive `ZG-Res-Key` response header as the response identifier.
8. Use only the documented chatbot body fallback, `data.id` or `data.chatID`, when the header is absent.
9. Reject an absent response identifier.
10. Call `processResponse(configuredProvider, responseIdentifier)`.
11. Require the result to be exactly `true`.
12. Only then extract and validate model content.

`false`, `null`, `undefined`, malformed results, and thrown verification errors all block the response. A verified response with invalid dialogue JSON is also rejected. No unverified tokens are streamed to the browser, and no raw provider body is returned in a public error.

Public verification metadata is limited to network, public provider address, model/service, response identifier, verification status and mode, provider-preflight status, completion time, and SDK version. 0G does not document a public explorer receipt for this response flow, so Alibi does not invent a receipt, transaction hash, or explorer URL.

## Testimony schema

The accepted model content is one strict JSON object:

```json
{
  "utterance": "string",
  "emotion": "neutral | guarded | anxious | angry | relieved",
  "action": "none | offer_lead | suggest_warrant | end_interview",
  "leadId": "approved ID or null",
  "predicateId": "approved ID or null"
}
```

Extra fields, Markdown fences, blank or oversized utterances, unknown values, and invalid action/identifier combinations are rejected. `offer_lead` requires an approved lead, `suggest_warrant` requires an approved currently available predicate, and all other actions require both identifiers to be `null`. The integration does not maintain a second predicate registry: the caller must supply the public, currently available predicate identifiers from the canonical registry after S1 is integrated.

## Prompt boundary

The server constructs a new allowlisted context rather than serializing a session and redacting it. The prompt may contain only:

- the selected public suspect identity, role, and non-canonical persona guidance;
- public room ID, name, and description;
- collected public observations;
- up to eight bounded turns from that suspect's conversation;
- approved lead identifiers;
- approved registered predicate identifiers; and
- the bounded current player question.

The four supported personas are Ada Vale, Marcus Reed, Celeste Moreau, and Theo Lin. Persona guidance is non-canonical and never identifies a guilty suspect.

The prompt cannot contain the hidden suspect, room, weapon, time, case index, hidden case object, salt, commitment opening, private witness, accusation plaintext, verdict material, candidate truth, session secret, signer material, prover credentials, Walrus/Seal secrets, human identifiers, environment values, arbitrary tools, network access, file access, database access, or client-supplied system messages. The 0G package does not depend on the game engine or any canonical transition function.

## Fixture and live behavior

- `fixture` runtime mode continues to use the existing deterministic fixture testimony, labelled `unverified-testimony`, without invoking 0G.
- `live` runtime mode never invokes fixture testimony and never creates a fixture session. Until S1 supplies a validated Sui-backed public session context and injects the live operation, the route returns the sanitized blocking `ZERO_G_LIVE_CONTEXT_UNAVAILABLE` 503 error.
- Accepted 0G testimony always returns `canonicalEffect: "none"` and `candidateMaskChanged: false`.
- A session/suspect pair permits one in-flight request and applies an in-memory cooldown. This prevents ordinary duplicates in one server process; it is not production-grade distributed rate limiting.

## Configuration

Keep credentials in the server secret store. Do not create a repository `.env` file, and never use these placeholder strings as real values.

```dotenv
ALIBI_ZERO_G_MODE=live
ZERO_G_NETWORK=<testnet-or-mainnet-label>
ZERO_G_RPC_URL=<https-rpc-url>
ZERO_G_PROVIDER_ADDRESS=<catalog-provider-address>
ZERO_G_MODEL=<catalog-model-identifier>
ZERO_G_SERVICE_TYPE=chatbot
ZERO_G_VERIFICATION_MODE=<TeeML-or-TeeTLS>
ZERO_G_REQUEST_TIMEOUT_MS=15000
ZERO_G_MAX_RESPONSE_BYTES=65536
ZERO_G_REQUIRE_PROVIDER_VERIFICATION=<true-or-false>
ZERO_G_REQUIRE_RESPONSE_VERIFICATION=true
ZERO_G_PRIVATE_KEY=<externally-supplied-server-secret>
```

Live parsing fails closed when a required value is missing or malformed. The private key is read only by the outermost server-only broker factory; core services accept an injected broker.

The live smoke harness sends exactly one paid inference using fixed public demo context. It prints only sanitized evidence and exits nonzero on any configuration, provider, inference, verification, or schema failure:

```powershell
# Supply all variables above through the process environment or secret manager first.
pnpm --filter @alibi/zero-g smoke:live
```

Do not repeat the smoke command unnecessarily. No live request should be attempted until the configured account is funded and the selected provider/model has been confirmed in the current service catalog.

## Account and provider preparation

According to the current official inference guide, Direct Compute setup requires an externally managed EVM-compatible signer, an 0G Compute ledger funded with at least 3 0G, and a provider subaccount funded with at least 1 0G. These values are documentation-derived and subject to change; re-check the official inference guide before funding. This repository never creates or funds the wallet.

For a judged run:

1. Select one healthy chatbot provider from the current catalog.
2. Record its public address, exact model, service type, and verification mode.
3. Configure the server secret and ledger/subaccount outside Git.
4. Run offline validation first.
5. Run the smoke harness exactly once, or use the final live web flow once wired.
6. Capture the real response identifier, successful SDK response-verification status, timestamp, public provider/model/network metadata, and code revision.
7. Demonstrate the injected forced-verification-failure test blocking a plausible response.

Never capture credentials, auth headers, signatures, raw prompts, environment dumps, provider bodies, or private persona text.

## Current limitations

- No real live inference evidence is committed; it requires external credentials, funds, and current provider configuration.
- S1 is not present in this lane, so the public route deliberately blocks live testimony until a Sui-backed public session context is injected.
- The B3 UI is not wired to pending/verified/blocked testimony states in this lane.
- The smoke command is integration evidence, not the final judged end-to-end web path.
- Provider catalogs and availability change; the explicit configured provider must still pass discovery on every fresh runtime.
- Automated provider preflight is not claimed as complete remote-attestation verification.
- Response verification proves the supported inference provenance path, not that testimony is factually or canonically true.
- In-memory duplicate/cooldown controls do not coordinate across server instances.
- There is no documented public explorer receipt for an inference response.
- Non-streaming is intentional because unverified tokens must never reach the browser.
- No deployment or public live link is created by this checkpoint.
